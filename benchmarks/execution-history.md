# Execution qualification and measurement history

These are historical observations on the pinned artifact and RTX 4090, not fresh measurements of the current head. See `model-set.toml` for artifact, reference, and workload metadata. Throughput-derived bandwidth estimates do not isolate an instruction or memory bottleneck, and results on this host do not qualify other devices. Proposed mechanisms and expected gains below are hypotheses pending matched measurement.

- Full-model async-vs-eager greedy parity against the pinned llama-server continuation passes on the RTX 4090, and identical serving sweeps before/after async adoption show unchanged ~1.8 tok/s aggregate: host-blocking removal alone does not move throughput while rows still execute sequentially through batch-1 kernels.
- Warp-cooperative quantized GEMV is landed and hardware-qualified: eight one-warp-per-row variants (coalesced lane-strided element runs, shuffle reduction) match the scalar oracle in per-family parity tests and reproduce the full 200-token llama-server greedy continuation in warp mode. A same-commit A/B serving sweep measures ~9.2 tok/s in warp mode vs 1.81 tok/s scalar (5.1x), flat across concurrency 1/2/4/8: the per-projection kernel was the bottleneck, and scheduler-batch members still execute sequentially through batch-1 kernels, which the remaining gap to the incumbent pace (~49.5 tok/s same artifact) attributes to. Warp is the executor default since `2d01c56` (user-approved on the measured evidence); scalar remains via `GemvMode::Scalar` / bench `--gemv=scalar`, and the scalar full-model replay pins its mode explicitly so oracle coverage survives the flip. Re-validated 44/44 on hardware after the flip.
- An nsys trace of warp-mode decode then showed the remaining single-thread correctness-first kernels dominating: `rms_norm` at 41.5% of GPU time (280 us per vector) and `argmax` at 4.75 ms per vocabulary scan. `2267630` replaced both (plus `l2_norm`) with one-block parallel reductions preserving the reference equations, tie, and NaN behavior; the CUDA suite re-passed 44/44 and the serving sweep moved to ~15.4 tok/s (1.68x over warp-only, 8.5x over the session baseline), still flat across concurrency because batch members remain sequential through batch-1 kernels.
- A second trace then showed `attn_score_gqa` (one thread per query head, 32 threads device-wide) at 11.3%. `9794181` gave each query head a full warp: coalesced F16 KV reads, shuffle-reduced dots, running-max softmax with exact rescaling, numerically identical to the reference. Suite re-passed 44/44 (165 s); the sweep reached ~20.3 tok/s (ITL 44 ms at c1), 11.2x the session baseline. Kernel-level work is now near exhausted per the trace: warp GEMV families are ~74% of remaining GPU time, so the next structural lever is native batched projections, as the sweep's flat-concurrency shape already indicated.
- Native batched execution is landed, hardware-qualified, and measured (`72e0908`-`b97e4d6`): batched warp GEMV (one warp per (row, member), consecutive warps sharing weight rows), batched embedding/norms/elementwise/rope/argmax, per-member state kernels over view-sliced rows, and a `CudaQwen35BatchDecode` executor running one launch per (layer, op) for every member. The dispatcher's submit seam picks it for multi-row all-decode greedy batches and falls back to the per-row path otherwise, with member physical states taken out of the registry for the step and re-inserted on every path so no device state is lost; per-member greedy tokens land in the same pinned slots through the existing completion-event machinery. Hardware qualification (51/51 CUDA suite incl. executor-level, dispatcher-level, real-geometry view-wrapper, and four-layer-prefix parity gates) caught and fixed three batched-path bugs: GDN q/k consumed never-written scratch, batched rope took dims instead of pairs, and `kv_append_f16_views` covered only 64 of 1024 cache elements at real geometry. The serving sweep moved concurrency-8 aggregate from a flat 20.3 tok/s to 25.0 tok/s (c1 unchanged at 20.2 tok/s / 44 ms ITL), the first concurrency win of the project; the remaining batched-step cost (~6.25x one member for 8) points at weight re-reads per member that the one-warp-per-(row, member) GEMV expects L2 to dedupe.

- The weights-read-once GEMV variant is landed and measured (`7ee9609`-`f390350`): an nsys trace of an 8-member batched run showed the per-(row, member) layout re-fetching every weight byte once per member - the 8 GEMV families were ~91% of batched GPU time. The kernels now keep one warp per weight row, decode each quantized element once, and accumulate against all members' inputs from unrolled register arrays (a runtime-bounded member loop spilled them to local memory and *regressed* concurrency-8 to 10.7 tok/s; the unroll-with-predicate fix restored register residency). Qualification: 51/51 CUDA suite, all batched parity gates. The sweep moved concurrency-8 aggregate from 25.0 to 31.7 tok/s (ITL 275 ms -> 205 ms) with concurrency-1 unchanged - the batched arc now stands at 20.3 flat sequential -> 25.0 batched -> 31.7 weights-read-once. Members are capped at 8 (the register accumulator width).
- Matched-incumbent serving comparison (2026-09-07, llama-server 0.3.0-dev b81c99b47, same artifact and request shape): llama.cpp c1/c2/c4/c8 measured 45.0/70.6/114.9/164.4 tok/s against engine 20.2/19.8/27.2/31.7 tok/s. Mean ITL at c1/c8 was 20.2/34.7 ms for llama.cpp and 44/205 ms for engine. Throughput-derived effective weight bandwidth suggests investigating kernel efficiency but does not establish memory traffic, compute saturation, or the cause of the gap.
- Kernel source comparison identified packed weight loads, integer `dp4a` dots, and Q8_1 activation packing in the incumbent single-vector path as candidates for the next engine variant. Reduced instruction pressure is a hypothesis pending matched profiling and measurements. Implement and qualify each weight family before model integration; activation packing is lossy, so kernel arithmetic checks alone do not establish full-model parity. Keep the float path as the reference and current default.
- The first integer-dot prerequisite is implemented as an experimental standalone `CudaQ8_1Quantizer`: caller-owned packed activation storage, asynchronous launch, and Q8_1 scale/input-sum metadata. Focused RTX 4090 tests cover byte layout, zero blocks, rounding ties, multiple scales, partial launch occupancy, scratch reuse, and invalid lengths. This does not yet integrate integer-dot GEMV or qualify model parity/performance; float execution remains the default.

## Lifecycle and preparation qualification, 2026-09-07

At `cec3c24`, the RTX 4090 release suite passed all 52 CUDA reference tests, both Q8_1 activation tests, and exhaustive conversion of all 65,536 F16 encodings. Reference coverage includes scalar and warp full greedy replay, batched/async parity, deferred physical release, and nine-request cancellation/fallback with successful peer completion and full physical reclamation. Host regression tests separately cover admission, malformed completion, atomic commitment, release retry, and qualification-scope mismatch. Device fault quarantine is tested with injected ownership/drain outcomes; no destructive device fault was induced.

The same pinned workload at `cec3c24` measured 20.16/19.98/27.40/31.79 aggregate tok/s at concurrency 1/2/4/8, with mean ITL 43.965/89.129/122.904/204.905 ms. This single sweep shows no material regression against the earlier baseline; it does not establish statistical equivalence. ## Kernel-level Q4_K float-vs-integer-dot A/B, 2026-09-08

At `317e7ca`, `q4_kernel_bench` compared qualified float warp GEMV against `quantize_q8_1` + `q4_k_q8_1_gemv` on synthetic `Q4_K` weights at three representative shapes (200 timed iterations each, per-launch stream synchronization, RTX 4090). Medians: 5120x5120 float 34.8 us vs integer-dot path 56.0 us; 5120x17408 float 96.8 us vs 154.3 us; 17408x5120 float 105.6 us vs 174.2 us. The integer-dot path is ~1.6x slower at every shape; `Q8_1` packing alone costs ~4 us, so the GEMV kernel itself is slower, not the packing. Relative output difference is ~0.5%, consistent with lossy activation packing on high-dynamic-range synthetic weights. These are synthetic-weight kernel timings, not model parity or serving throughput; the pinned artifact's real tensor distribution (131 `Q5_K`, 117 `IQ4_XS`, 106 `Q8_0`, 104 `Q4_K`, 30 `Q6_K` tensors) means `Q4_K` alone cannot move full-model pace. Suspected mechanism (hypothesis, not a profiled fact): the integer-dot kernel issues ~40x more `decode_f16` calls per GEMV than the float warp kernel (per-lane activation scale/sum decodes plus header decodes, each with branches and exponent-shift loops) which may dominate the saved float dequant work. Next step is to profile before expanding families: confirm with nsys, reduce redundant decodes, and re-measure. Family expansion (`Q5_K`/`Q6_K`/`IQ4_XS`), batched integer-dot shapes, and model integration stay gated on a kernel-level win.

At `9f45c01`, nsys confirmed the gap at kernel level (`q4_k_q8_1_gemv` median 149.8 us vs `q4_k_gemv_warp` 93.9 us, 1.6x; packing ~1.2 us) and the decoder hypothesis held: swapping only the experimental kernel's four `decode_f16` call sites to a local bit-rebias converter (same contract, qualified float families untouched) moved the path to 28.9/72.3/83.0 us against float 34.9/97.0/105.9 us across the three shapes — a 1.2-1.34x kernel-level win with unchanged ~0.5% relative difference on synthetic weights. The two `q4_q8_1` CUDA qualification tests still pass. The win is kernel-level on synthetic weights, not model parity or serving throughput; family expansion is now unblocked but each family still needs its own implementation, error bounds, and matched measurement.

At `43d6b44`, `Q5_K` joined as the second integer-dot family (`CudaQ5KQ8_1Gemv` + `q5_k_q8_1.cu`): same warp-per-row structure with the 5-bit quant reconstructed as low nibble | (high-plane bit << 4) per dp4a lane. Two host arithmetic tests and two RTX 4090 CUDA tests mirror the `Q4_K` qualification (exact/lossy fixtures with 5-bit quants through both planes, packed-arithmetic match with explicit float error bound, invalid-storage rejection). The generalized bench measures a kernel-level win at every shape: 5120x5120 29.9 vs 37.6 us (1.26x), 5120x17408 75.3 vs 106.8 us (1.42x), 17408x5120 80.8 vs 115.8 us (1.43x), with ~0.4% relative difference. `Q4_K` re-measured in the same run at 1.21-1.34x. Remaining families (`IQ4_XS`, `Q3_K`, `Q8_0`), batched integer-dot shapes, and model integration stay unfinished.

At `c3576ed`, `Q6_K` joined as the third integer-dot family (`CudaQ6KQ8_1Gemv` + `q6_k_q8_1.cu`): sixteen lanes each own one (group, half) tile of 16 values with per-half signed scales, and the signed 6-bit quants need no affine minimum term — the -32 bias folds into exact ones-vector dp4a half sums over the same activation words. Two host arithmetic tests and two RTX 4090 CUDA tests mirror the earlier qualifications. The work caught a real portability bug: 210-byte `Q6_K` blocks are not u32-aligned, so weight words load byte-wise (`3ba37be`); the 144/176-byte `Q4_K`/`Q5_K` blocks are unaffected. The generalized bench measures a narrower but consistent kernel-level win: 5120x5120 32.5 vs 35.0 us (1.08x), 5120x17408 90.3 vs 101.1 us (1.12x), 17408x5120 95.9 vs 107.2 us (1.12x), with ~0.4-0.7% relative difference. `Q6_K` covers 30 tensors including the 1.27 GB output projection.

At `7fb0299`, `IQ4_XS` joined as the fourth integer-dot family (`CudaIq4XsQ8_1Gemv` + `iq4_xs_q8_1.cu`): weight nibbles resolve through the 16-entry signed codebook kept in shared memory with eight replicas to avoid bank conflicts, filled once per threadblock before the row guard. Scales are small integers, so the only F16 decodes are d and the activation scale — the cleanest arithmetic of the four, with no sum or minimum terms. Two host arithmetic tests and two RTX 4090 CUDA tests mirror the earlier qualifications. The bench measures the largest win yet: 5120x5120 19.8 vs 33.2 us (1.68x), 5120x17408 46.9 vs 96.1 us (2.05x), 17408x5120 51.9 vs 101.1 us (1.95x), with ~0.4% relative difference and ~1010 GB/s effective weight bandwidth at the large shape — the kernel is now memory-bound. `IQ4_XS` covers 117 tensors, the FFN bulk. Remaining families (`Q3_K`, `Q8_0`, plus small `Q6_K`-class stragglers), batched integer-dot shapes, and model integration stay unfinished.

At `d3e7485`, the first batched integer-dot variant landed as the `Q4_K` template (`q4_k_q8_1_gemv_batch` + `CudaQ4KQ8_1Gemv::execute_batch`): one warp per weight row reuses each decoded element across up to eight batch-major members, mirroring the float weights-read-once structure including register-resident predicated accumulators. Two RTX 4090 CUDA tests qualify it (three distinct members against per-member host arithmetic and error bounds; zero/ninth-member and short/long storage rejection). The bench measures a batch-8 win at every shape: 5120x5120 151.0 vs 167.5 us (1.11x), 5120x17408 359.1 vs 578.7 us (1.61x), 17408x5120 501.6 vs 569.4 us (1.13x), with ~0.5-0.7% relative difference. Both batch paths are compute-bound at eight members; the comparison of interest is same-work int-vs-float, which integer-dot wins. Batched variants for the other three families, then model integration with full-model parity, stay next.

At `af2dda8`, the second batched variant landed for `Q5_K` (`q5_k_q8_1_gemv_batch` + `CudaQ5KQ8_1Gemv::execute_batch`), adding the high-bit-plane gather to the `Q4_K` batch template; the bench batch section now covers both families. Two RTX 4090 CUDA tests mirror the `Q4_K` batch qualification. Batch-8 wins at every shape: 5120x5120 153.3 vs 171.6 us (1.12x), 5120x17408 385.3 vs 569.3 us (1.48x), 17408x5120 503.2 vs 580.7 us (1.15x), with ~0.4-0.5% relative difference. Batched `Q6_K`/`IQ4_XS` and model integration stay next.

At `e5fe529`, the third batched variant landed for `Q6_K` (`q6_k_q8_1_gemv_batch` + `CudaQ6KQ8_1Gemv::execute_batch`): the 16-lane tile mapping with per-member activation words and ones-vector half sums. Two RTX 4090 CUDA tests mirror the earlier batch qualifications. Batch-8 wins: 5120x5120 134.8 vs 183.6 us (1.36x), 5120x17408 375.6 vs 594.1 us (1.58x), 17408x5120 446.0 vs ~958-1533 us float (2.1x against the float path's best minute; its median sits near 1.5 ms with a wide spread reproduced across runs, so that ratio carries a measurement caveat while the integer-dot side stays tight). Relative difference ~0.3%. Batched `IQ4_XS` and model integration stay next.

At `ec49aa4`, the fourth and last planned batched variant landed for `IQ4_XS` (`iq4_xs_q8_1_gemv_batch` + `CudaIq4XsQ8_1Gemv::execute_batch`): per-lane codebook quads resolve once and reuse across all members, with per-member activation words, dots, and scales. Two RTX 4090 CUDA tests mirror the earlier batch qualifications. Batch-8 wins are the largest of the track: 5120x5120 48.2 vs 170.1 us (3.53x), 5120x17408 131.7 vs 554.3 us (4.21x), 17408x5120 154.5 vs 566.0 us (3.66x), with ~0.25% relative difference and tight distributions on both sides. The float `IQ4_XS` batch path is particularly expensive per member, so the reuse pays off more than in the K-quant families. All four single-row and all four batched integer-dot families are now qualified with measured wins; model integration with full-model parity is next.

At `a521cab` (+`23e02f3`, `728f354`), batch-1 integer-dot reached the model: `GemvMode::IntegerDot` with a lazily built executor-side `CudaIntDotProjector` (shared quantizer, four int kernels, realloc-on-width-change packed scratch), per-tensor float-warp fallback for `Q3_K`/`Q8_0`/`IQ4_NL`/`IQ3_S`, and `--gemv=int-dot` plus `--print-tokens` in the serving bench. RTX 4090 concurrency-1 200-token A/B: token sequences identical 200/200 across independent runs (lossy packing perturbs nothing the greedy argmax can see on this prompt), throughput 20.6 vs 21.3 tok/s (int-dot ~3% slower; the per-projection pack pass is not amortized at batch 1, as predicted — kernel wins need batch > 1). Batched-executor integration and the concurrency sweep stay next.

At `2951766` (+`241d0f9`), the batched executor followed: `CudaQwen35BatchDecode` carries its own `GemvMode` (seeded from the single executor at dispatcher construction), per-`gemv_batch` mode/projector plumbing with batch-major packed scratch (one quantizer launch over all members, then one weights-read-once integer-dot launch), and float fallback to `execute_warp_batch` per tensor. All 52 pinned-model CUDA reference tests still pass unchanged. Matched RTX 4090 serving sweep (concurrency-1 baseline 21.2 warp / 20.3 int-dot, per earlier batch-1 finding), identical prompts/steps per mode, 64 output tokens:

| 2 | 20.98 | 25.88 | 1.23x | 89.9 ms | 70.9 ms |

All eight members' token streams at concurrency 8 were token-identical to the warp baseline across the 64-token run (same prompt, independent run), matching the batch-1 divergence result: the greedy path is insensitive to the ~0.3-0.5% packing perturbation on these prompts. The serving-level win (1.23-1.32x) is real but below the pure-kernel batch-8 ratios (1.1-4.2x) because projections are only part of each step: attention/GDN state kernels, norms, embedding, argmax, and quantizer launches are unchanged, and the concurrency-8 step remains launch-latency and non-GEMV bound. For reference, the imported incumbent baselines (llama.cpp DFlash2, `benchmarks/incumbent-qwen38/RESULTS.md`) sit at 90-123 tok/s on this GPU with speculative decoding; closing that gap is a separate, larger effort (scheduler overlap, CUDA graphs, draft paths) beyond this kernel track.

The int-dot quality gate ran at `07c954a`: the serving bench gained `--divergence-probe` (six fixed diverse prompts distributed per request slot, including one deliberately near-tie-prone repeated-token prompt, with KV capacity sized to the longest). Matched 1024-token greedy generations under warp vs int-dot at concurrency 6: all six prompts token-identical across the full horizon, matching the earlier 200- and 64-token results. The greedy path stays insensitive to the ~0.3-0.5% packing perturbation across every prompt profile tested. The mode remains opt-in by policy — this is evidence, not a proof, and a default flip would want broader sampling (non-greedy, longer contexts, adversarial prompts) — but no divergence has been observed on any tested workload.

At `45b20de`, a post-track nsys trace (`/tmp/qwen-batch8-after.nsys-rep`) showed the int-dot batch kernels leading decode but `q8_0_gemv_warp(_batch)` still holding ~9% of GPU time as the largest uncovered family, so `Q8_0` joined the integer-dot track (`q8_0_q8_1.cu` + `CudaQ8_0Q8_1Gemv`): weights are already signed bytes with one `F16` scale per 32 values, so the kernel needs no nibble unpacking — each lane owns one four-byte payload word via byte-wise assembly (the 34-byte block stride never guarantees `u32` alignment, the same lesson `Q6_K` taught) against one packed activation word per block, with the K-quant four-block tile mapping (lanes cover eight chunks of four consecutive blocks; an earlier all-lanes-per-chunk draft quadruple-counted and was caught by the host parity test). Two RTX 4090 CUDA tests mirror the other families; all 52 pinned-model reference tests still pass. Kernel batch-8 wins: 5120x5120 74.3 vs 138.3 us (1.86x), 5120x17408 246.6 vs 430.3 us (1.74x), 17408x5120 283.3 vs 571.0 us (2.02x). Serving c8 64-token A/B: 45.92 vs 34.59 tok/s (1.33x, up from 1.32x — `Q8_0` is a small share of the model's tensors). Divergence gate re-run with `Q8_0` in the mix at 256- and 1024-token horizons: all six diverse prompts token-identical to warp. Float fallback now covers only `Q3_K`/`IQ4_NL`/`IQ3_S`.
